The display controller keeps manual choices in effect until you explicitly select
Auto. Raycast, the `bd-*` commands, the AeroSpace mode chord, and Sketchybar use
the same controller. Wake recovery restores the current intent, including custom
values, rather than replaying a preset captured before a retry.

## Everyday controls

| Command | Behavior |
| --- | --- |
| `bd-night`, `bd-read`, `bd-meeting`, etc. | Select a preset and enter Manual |
| `bd-manual` | Hold the current managed intent; disable competing native auto-brightness |
| `bd-auto` | Resume ambient-light control; wait if the sensor is unavailable |
| `bd-up` / `bd-down` | Adjust both displays by 10 points and hold; optional `dev` or `port` |
| `bd-set port 35` | Set external luminance to 35, as a manual choice |
| `bd-set dev 80` | Set built-in software brightness to 80%, as a manual choice |
| `bd-backlight 30` | Set built-in hardware brightness to 30% and software brightness to 100% |
| `bd-save night` | Save the current successfully managed values as your Night preset |
| `bd-stream` / `bd-stream-stop` | Enter Stream and restore the preceding choice afterward |
| `bd-status` | Show ownership, requested values, and last outcome |

The percentages above are examples of command syntax, **not calibrated nits**.
Use `bd-backlight` for ordinary built-in brightness calibration. After hardware
brightness is lowered below 100%, `bd-up/down dev` adjust hardware brightness;
otherwise they adjust software brightness. `bd-srgb` and `bd-xdr` remain explicit
color/brightness choices. They restore hardware to 100% and select their existing
software targets (100% and 160% respectively).

Raycast has **Brightness · Auto**, **Manual hold**, **Increase**, **Decrease**, and
**Status**, plus the existing preset commands. AeroSpace `Alt+Shift+X` enters the
mode chord: `u` resumes Auto, `h` holds, and the existing preset keys remain.
Sketchybar left/right clicks cycle presets; middle click selects Auto. Its label
shows ownership and requested percentages: `H` is built-in hardware and `S` is
built-in software. Pending, failed, unverified, and unavailable sensor states
remain visible.

The supported manual inputs are these commands and Raycast actions. Arbitrary
BetterDisplay menu/slider or native-key changes are not captured automatically.
They can change the image without updating the controller's saved values. Use
managed controls when you want an adjustment to survive wake and recovery.

## Ownership and persistence

- `~/.cache/bd-intent.json` is the authoritative, versioned intent: owner, base
  values, HDR override, serial identities, revision, source, and per-display outcome.
- `~/.cache/bd-state` is a compatibility projection for older readers.
- The first migration backs up the old projection to `bd-state.before-intent-v1`
  and starts in Manual. It does not change brightness. Unknown legacy names or
  malformed/future intent data fail visibly rather than being overwritten.
- Calibrated presets live outside the checkout at
  `~/.config/dotfiles/display-profiles.json`; saving a replacement retains a
  `.previous` backup. No calibration changes the factory presets in source.
- One OS file lock on `~/.cache/bd-apply.lock.file` covers request selection,
  identity resolution, hardware writes, and outcome persistence. Contention returns
  75 after 30 seconds without changing intent. A legacy lock directory is left
  for inspection rather than removed automatically.

Manual always takes priority over ambient requests. HDR temporarily overrides
external brightness and suspends ambient selection while preserving the base
choice. Returning from HDR restores that choice. Every wake retry reloads intent
under the lock, so an older wake request cannot overwrite a newer manual choice.

The controller's Auto mode is **its ambient watcher**, not macOS Auto Brightness.
Managed applies keep the Apple display's native auto-brightness off, with readback,
to prevent a second automatic loop from changing the requested values. True Tone,
Night Shift, gamma tuning, and color calibration are separate settings.

## Factory presets and calibration

These are the inherited factory values, retained for compatibility—not a claim
that they are optimal for your room or eyesight. All use the Apple XDR display
preset and built-in hardware brightness 100% until you save calibrated overrides.

| Mode | Built-in software | External luminance |
| --- | --- | --- |
| Dawn | 100% | 55 |
| Day | 105% | 100 |
| Afternoon | 100% | 85 |
| Evening | 80% | 55 |
| Night | 60% | 35 |
| Meeting | 130% | 100 |
| Read | 100% | 85 |
| Stream | 120% | 90 |
| Cinema | 150% | 80 |

Contrast and temperature on the external display are independent of this table:
`DOTFILES_BD_PORT_REF_CONTRAST` defaults to 75, temperature to 0, and gamma to 0.
Gamma 0 means leave gamma untouched. The unused per-mode color columns were removed.

Read [luminance research and calibration](/display/luminance/) before choosing
new values. Brightness percentages cannot be converted to nits using the maximum
brightness specification. Save each preset only after adjusting it in the room
conditions where you use it. Keep HDR off during SDR calibration.

## Hardware and proof levels

Implementation is under `scripts/scripts/lib/display_control/`: `policy.py` owns
state and presets, `hardware.py` owns bounded BetterDisplay requests, and `cli.py`
owns locking and execution. `bd-apply.sh` is the shell/personal.env entry point.

The built-in hardware brightness, software brightness, color preset, and native
auto-brightness are read back. The external display uses raw DDC VCP luminance and
contrast writes, retaining the existing workaround for this rig. Software
color-temperature and HDR state are read back. Accepted external VCP commands are
reported as **dispatched**, not verified physical luminance. Failures from either
display make the command return nonzero; pending ambient work retries at the
next poll even when the sensor bucket has not changed.

Registered displays are resolved by role and serial. A serial recorded by the
controller survives a tag-ID change. `DOTFILES_BD_DEV_SERIAL` and
`DOTFILES_BD_PORT_SERIAL` can pin a specific device in `personal.env`; ambiguous
or mismatched identities fail before any write. Legacy numeric tag overrides are
not used as identity authority. No 'first external display' guess is made.

`bd-apply.sh doctor` reports identities and installed app metadata; `verify`
compares readable values with the saved intent. Neither claims physical DDC
readback. Never use `betterdisplaycli version` as a diagnostic; read bundle metadata.
Command timeouts are bounded. No formatter, package manager, account, or provider
installation is involved in display control.

## Automation and wake

`bd-lmu-watch.sh` polls every 60 seconds. Thresholds remain 50 / 200 / 600, with
15% hysteresis; the four buckets select Night / Evening / Afternoon / Day. Treat
sensor readings as the current sensor's scale, not a calibrated room lux meter.
The five old fixed-hour timers are retired; they are not reinstalled by this work.

The registered sleepwatcher agent handles system wake, and `unlock-watch` handles
screen unlock. Both call `~/.wakeup` → `bd-wake.sh`. The watcher also retains a
software-availability recovery probe; it is not proof that a DDC panel answered.

## Layout and HDR

`display-restore.sh` owns seven profiles: Daily, Stream, Hires, Native, Portrait,
Portrait-hires, and Solo. It routes writes through the same lock. `--dry-run`
always wins over `--force`, independent of order. Failed commands or failed layout
readback retain the last confirmed profile and return nonzero.

| Profile | Built-in | External |
| --- | --- | --- |
| `--daily` | 1728×1117 | 1920×1080 |
| `--stream` | 1728×1080 | 1920×1080 |
| `--hires` | 1728×1117 | 2560×1440 |
| `--native` | 3456×2234 | 3840×2160 |
| `--portrait` | 1728×1117 | 1080×1920, 90° |
| `--portrait-hires` | 1728×1117 | 1440×2560, 90° |
| `--solo` | The single connected display | Defaults to 2560×1440 on an external |

The current rig's preferred layout is Portrait-hires; an empty layout cache still
falls back to Daily. Explicit layout overrides use `DOTFILES_DISPLAY_LAYOUT`.
The helper retains existing UUID discovery/profile behavior; more complex
multi-monitor layout ownership is a separate configuration task.

`bd-hdr-toggle.sh on|off|toggle` delegates to the controller. On uses the configured
HDR brightness (default 100), Off restores base luminance. Brightness failures are
reported even when HDR itself changes successfully. `bd-build-slots.sh` remains
an explicitly invoked favorite-slot recovery tool; it uses the shared executor
and, as before, finishes by selecting Day. Virtual-screen connection is no longer
an implicit side effect of the Stream brightness preset.

## Verification and reload

Run the isolated fixtures in `tests/test_display_control.py` and
`tests/test_display_layout.py`, along with the existing regression checks in
`VERIFY.md`. They intercept all hardware writes. Live physical luminance and
comfort checks require observation or a meter and are a separate validation step.

New shells pick up aliases. Reload the rendered AeroSpace configuration when
ready. A running ambient watcher must restart to load its revised retry loop;
existing old watchers are compatible with the controller's manual protection
during the transition. General `update.sh` still performs no extra service restart.
