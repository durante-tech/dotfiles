`./personalize.sh` edits a small set of supported preferences without changing
shared defaults. It preserves unknown settings and complete multiline values,
shows a preview, validates the result, and keeps a backup before applying.

## Start here

```bash
cd ~/dotfiles
./personalize.sh show
./personalize.sh list-apps
./personalize.sh                     # interactive preview, then an apply prompt
./personalize.sh --recheck           # also query current display identities/names
./personalize.sh --dry-run           # preview only; no live hardware discovery
```

The wizard starts from current values. Enter keeps a value unchanged. The optional
GUI editor is initially unconfigured; choosing it does not change the terminal's
`EDITOR` setting. Existing default launch choices remain Ghostty, Chrome, and Notion.

## Files and precedence

| Source | Purpose |
| --- | --- |
| Shared repository defaults | Base values and app-category routing |
| `~/.config/dotfiles/personal.env` | Existing machine values and custom shell assignments |
| `~/.config/dotfiles/preferences.json` | Validated overrides managed by the personalizer |
| `~/.zprofile.local` / `~/.zshrc.local` | Final login/interactive shell customizations |

For the supported preferences, explicit `preferences.json` values override legacy
literal assignments, which override repository defaults. `show` reports this
source for each setting. Shell-local overrides can still change a particular
shell's environment; `show` describes the shared preference inputs, not arbitrary
code executed by a running shell.

Initialization inputs such as `DOTFILES_GCLOUD_SDK_DIR` belong in `personal.env`,
which is loaded before tool initialization. The local Zsh hooks run afterward.
The existing agent-safety guard still follows `.zshrc.local`, and profiling runs
last. Project formatter configuration retains its own authority.

## Supported settings

Run `./personalize.sh catalog` for the authoritative field/type/consumer catalog.

| Settings | Values and consumers |
| --- | --- |
| `apps.terminal` | Installed bundle ID; AeroSpace Alt+Enter and `dotfiles-app terminal` |
| `apps.browser` | Installed bundle ID; Hyper+O+C and `dotfiles-app browser` |
| `apps.notes` | Installed bundle ID; Hyper+O+N and `dotfiles-app notes` |
| `apps.editor` | Optional GUI editor bundle ID; preferred routing and `dotfiles-app editor` |
| `workspaces.terminal/browser/editor/notes` | Existing persistent workspace names, default T/B/D/N |
| `monitors.builtin/external` | Regular expressions used by AeroSpace monitor pinning |
| `display.builtin_serial/external_serial` | Optional serial pins used by the display controller |
| `projects.roots` | JSON array of absolute or home-relative project roots |

The app/workspace mapping affects the existing category routes as well as the
preferred app. Role navigation and move shortcuts agree: Alt+T/B/D/O follow the
configured destinations, as do their Shift variants; Hyper+N follows Notes.
Finder, screenshot-tool, and automation-browser floating exceptions are retained.
Existing windows are not moved by the personalizer.

App preferences are bundle IDs, not shell commands. `list-apps` reads installed
app metadata; the wizard accepts a number from that list. Missing or ambiguous
selected installations fail visibly. The same app cannot be assigned to two
roles with different workspace destinations. No tool installs are performed.

## Preview and apply examples

These examples illustrate the interfaces; choose values appropriate for your setup.

```bash
./personalize.sh set apps.browser com.apple.Safari
./personalize.sh set apps.browser com.apple.Safari --apply
./personalize.sh set workspaces.terminal 2 --diff
./personalize.sh set workspaces.terminal 2 --apply
./personalize.sh set projects.roots '["~/Developer", "~/Work Projects"]' --apply
./personalize.sh set apps.editor com.microsoft.VSCode --apply
./personalize.sh reset apps.editor --apply
```

`set`, `reset`, and `undo` preview by default. `--apply` writes the validated plan;
`--dry-run` wins in either argument order. `--diff` additionally shows the proposed
AeroSpace diff. Unknown/private environment content is not printed in previews.

For optional settings, `null` explicitly disables the override's value. For an app
role it leaves the launcher unconfigured. For serials it uses the display
controller's learned identity. `reset KEY` removes the managed override and returns
to the legacy/default value. Numeric workspace names and serials remain strings.

If editing `preferences.json` manually, keep the versioned shape and run:

```bash
./personalize.sh apply --dry-run
./personalize.sh apply
./personalize.sh check
```

## Preservation, validation, and undo

The personalizer never sources `personal.env` while reading, previewing, or
editing it. It preserves all user content and adds an owned block at EOF for the
few preferences that existing shell consumers need. It does not reconstruct
unknown variables with line-based grep. Keep user additions above that block;
edit managed values through `set`/`reset` or `preferences.json`.

Simple legacy literal assignments—including quoted multiline values—are read as
fallbacks. Dynamic shell expressions for known settings require an explicit
preference before rendering. Invalid shell syntax, malformed/future JSON,
unsupported fields, invalid patterns, and unknown workspace names stop before
writes. Files are validated before replacement, with atomic writes and rollback
on a write failure. Concurrent edits detected after preview are preserved.

Backups live under `~/.config/dotfiles/backups/personalization-*`. The apply output
prints the exact backup name. Undo refuses to overwrite inputs changed since the
apply, and can be previewed:

```bash
./personalize.sh undo BACKUP_NAME
./personalize.sh undo BACKUP_NAME --apply
```

A render-only update does not rewrite preferences or create an empty preference
file. It backs up changed generated configuration. Rendering requires Python
3.11+ or an already installed Bun for TOML validation; neither is installed by
this tool.

## Reload and deployment boundaries

App launchers read saved preferences at invocation. After changing routing, reload
AeroSpace when ready:

```bash
aerospace reload-config
```

The personalizer prints reload instructions instead of reloading apps or restarting
services. New shells pick up projected environment settings. Display calibration
and Manual/Auto ownership remain in their existing files and are not reset by
personalization; see [display controls](/display/).

Edit `aerospace/templates/aerospace.toml.template` for structural changes. The
rendered `aerospace/.config/aerospace/aerospace.toml` is generated output and should
not be edited directly. Stow remains per package, using `stow-packages.txt`:

```bash
./setup.sh --stow
# Or specific packages:
stow -R -t ~ zsh scripts aerospace karabiner
```

A custom `DOTFILES_DIR` stays in `personal.env` for existing daemon contexts. The
root personalizer derives its checkout location or honors an exported
`DOTFILES_DIR`; runtime helpers honor `personal.env`. For test/alternate profiles,
`DOTFILES_USER_CONFIG_DIR` selects the configuration directory. This first batch
keeps profiles explicit; it adds no automatic context switching.

## Legacy settings

Unknown values are retained. Numeric BetterDisplay tag variables and
`DOTFILES_KEYBOARD_LAYOUT` may remain for older tooling, but the personalizer does
not advertise them as active controls. Display identity is serial-based. The
existing accent-safe keyboard bindings remain unchanged until a separate keyboard
customization feature is requested.
